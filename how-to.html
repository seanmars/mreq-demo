      00 · 問題

      一句需求, 藏著沒說出口的決策

      假設你對 agent 說: 「待辦加上到期日.」 這句話看起來很清楚. 但是 agent 開始寫程式之前, 至少要決定下面三件事:

      • 「今天」以哪個時區為準?
      • 舊的待辦沒有到期日, 讀取時怎麼處理?
      • 過期要怎麼標示? 要不要排序?

      你沒說的事, agent 會自己決定. 它通常不會告訴你它做了什麼決定. 你只會在結果不符合預期時才發現.

      MREQ 的做法

      mreq 是一組 skill. 它讓 agent 先問, 再做. agent 先讀程式碼, 再用選項問你決策, 然後重述需求等你確認. 需求比較大時, 結論會寫成 .mreq/ 下的一份文件. 這份文件是需求的單一來源, 也是給下一個 session 的交接單.

      你會在這份指南學到

      1. 小需求怎麼用 mreq 處理, 而且不產生文件.
      2. 完整流程: define, grill, apply, (commit), close.
      3. 修 bug 時, mreq 怎麼要求先重現, 再確認根因.
      4. 每一步要觀察的重點, 以及背後的原因.
      01 · 概念

      mreq 的 skill 與流程

      mreq 有 8 個 skill. 這份指南主要使用前 4 個. 「誰能呼叫」很重要: 只有使用者能呼叫的 skill, agent 不會自動執行. agent 只會給你完整的指令, 讓你自己輸入.

      SKILL作用誰能呼叫
      mreq-define判斷意圖, 訪談, 重述, 確認後寫文件. 小需求可以不寫文件, 直接實作.只有使用者
      mreq-grill用四象限壓力測試文件, 把結論寫回文件.使用者, agent
      mreq-apply逐項實作文件的 Tasks, 更新 checkbox 和 Handoff.使用者, agent
      mreq-close核對程式碼與文件, 通過後刪除文件.只有使用者
      mreq-terms / mreq-pro補術語, 加深 prompt. 想法還模糊時使用.只有使用者
      mreq-how / mreq-graph產生解說程式碼或畫圖的離線 HTML. 不改程式碼.只有使用者

      互動流程圖

      流程圖會自動播放. 點任何一個節點, 可以停下來看那一步的說明. 虛線框是選用的步驟.

      標準流程 · 產生 .mreq/ 文件
      小需求 · 不寫文件
      自動接續

      skill 之間能自動接續的地方, 你不需要輸入指令. 例如 define 的確認選項同時決定下一步: 選「寫文件, 然後 grill」, agent 寫完文件就直接開始 grill. 只有 /mreq-define 和 /mreq-close 這類「只有使用者」能呼叫的 skill 不會被自動接續.

      02 · 準備

      準備環境

      選擇你的 shell

      有些指令在 PowerShell 和 Bash 的寫法不同. 這些終端機區塊的標題列有 shell 分頁. 在任何一個地方切換, 整份文件都會一起切換, 並記住你的選擇.

      需要的工具

      • Node.js 22.20 以上 (建議 24). 專案本身需要 22.18 以上, 安裝 skill 用的 npx skills 需要 22.20 以上. 這個專案直接執行 .ts, 不需要編譯.
      • uv, 或 Python 3.10 以上. mreq 的 script 用它來建立和更新文件. 沒有 uv 時, skill 會自動改用 python.
      • git 和 Claude Code.
      1. 在 demo 專案安裝 mreq skill

        在 mreq-demo 目錄執行. 這個指令使用 vercel-labs/skills CLI, 把全部 mreq skill 安裝到這個專案.

        mreq-demo
        npx skills add seanmars/mreq --skill '*' -a claude-code
        • --skill '*' 選擇全部 skill. mreq 的 skill 之間會自動接續, 例如 define 接 apply, 所以要全部安裝.

        • 不要加 -g. 這份指南假設 skill 安裝在專案內.
        • 用這個方式安裝時, 指令沒有前綴, 直接輸入 /mreq-define.
        注意

        已經用 Claude Code plugin 安裝過 mreq 時, 先移除 plugin. 兩種方式同時存在時, Claude Code 會載入兩份 skill. 安裝完成後才啟動 claude, 這樣它才會讀到新的 skill.

      03 · 場地

      認識 demo 專案: mreq-todo

      這是一個 TypeScript 寫的 TODO CLI. 它有 4 個指令: add, list, done, rm. 資料存在 todo.json, 也可以用 TODO_FILE 環境變數改路徑.

      檔案內容
      src/todo.tsTodo 型別和所有邏輯: 新增, 完成, 刪除, 篩選, 格式化.
      src/store.ts讀寫 JSON 檔.
      src/cli.ts解析參數, 呼叫上面兩個模組.
      scripts/seed.ts寫入 4 筆範例資料.
      test/todo.test.ts9 個測試, 全部通過.

      先執行一次, 看看真實的輸出:

      mreq-demo
      npm run todo -- list -- --all[x]   1  買牛奶[ ]   2  回覆客戶信件[ ]   3  繳電話費[ ]   3  準備週會簡報
      npm run todo -- list --all[x]   1  買牛奶[ ]   2  回覆客戶信件[ ]   3  繳電話費[ ]   3  準備週會簡報
      為什麼 PowerShell 有兩個 --

      在 PowerShell 中, npm 可能是 npm.ps1 這個 PowerShell script, 而 PowerShell 會吃掉第一個 --. 只寫一個 -- 時, --all 會被 npm 當成自己的選項, 不會傳給 CLI. 所以 PowerShell 分頁中帶選項的指令有兩個 --.

      Bash 和 zsh 不會吃掉 --, 所以只寫一個. cmd 也一樣, 請使用 Bash 分頁的 npm 指令. 寫錯時的症狀: list 只列出未完成的待辦, 少了「買牛奶」.

      看起來很普通. 但是這個專案藏了兩個陷阱. 先仔細看上面的輸出和 scripts/seed.ts, 試著自己找出來. 然後再打開下面的答案.

      打開答案: 兩個陷阱

      陷阱 1: 重複的 id (Demo 3 會修)

      src/todo.ts:16 用 id: todos.length + 1 產生新 id. 刪除一筆之後再新增, 新的 id 會和現有的 id 重複. 輸出裡有兩筆 #3, 就是這個 bug 的結果. 而且 done 和 rm 會比對所有相同 id 的待辦, 所以 done 3 會同時勾掉兩筆.

      陷阱 2: UTC 與「今天」(Demo 2 的 grill 會找)

      createdAt 存的是 UTC (src/todo.ts:19, toISOString()). 範例資料的第 4 筆是 2026-11-24T16:30:00.000Z. 這個時間在台灣已經是 11 月 25 日 00:30. 如果到期日的「今天」用 UTC 計算, 台灣的使用者在凌晨會看到錯誤的過期判斷.

      為什麼要放陷阱

      陷阱讓你可以檢查 mreq 的品質. 一個好的流程應該在寫程式之前, 就把這兩件事變成問題問你. 觀察 agent 有沒有找到它們, 比觀察它寫出什麼程式碼更重要.

      DEMO 1 · 小需求 · 約 5 分鐘

      小需求不寫文件, 直接做

      /mreq-define list 加上 --count 顯示總數

      這個 Demo 的目的: 讓你看到 mreq 不是每次都要寫文件. 需求很小時, 它仍然會先確認, 但確認之後直接實作.

      1. 在 Claude Code 輸入指令
        claude · mreq-demo
        /mreq-define list 加上 --count 顯示總數
      2. 觀察 agent 先讀, 再問

        agent 不會馬上寫程式. 它會依序做這些事:

        • 執行 git rev-parse --show-toplevel, 確認 git root.
        • 用 mreq 的 script 執行 list --open, 確認沒有已經在進行的文件.
        • 讀 README.md, CLAUDE.md, src/cli.ts, src/todo.ts 和測試.
        • 判斷需求的大小. 這個需求只動到 list, 所以是 Simple.
        • 判斷需求的類型. 「加上」是新增行為, 所以是 feature.
        為什麼

        規則是「程式碼能回答的問題, 不問使用者」. agent 先讀程式碼, 所以它問的問題會很具體, 而且只問程式碼無法決定的事.

      3. 回答訪談問題

        需求很清楚時, agent 可能不問任何問題. 有決策需要你做時, 它會用 AskUserQuestion 給你選項. 下面是可能出現的問題 (實際文字會不同):

        範圍AskUserQuestion
        --count 和 --all / --done 一起使用時, 總數要算哪個範圍?
        1. 跟著篩選(Recommended)總數等於列出的筆數. 和現有的篩選行為一致.
        2. 一律算全部不管篩選條件, 都顯示全部待辦的數量.
        3. 只顯示數字加上 --count 時不列出待辦, 只印出數字.
        選項下方有文字欄. 沒有你要的答案時, 直接輸入.

        注意選項的結構: 推薦的答案在第一個, 而且說明裡寫了推薦的原因. 決策不影響主要工作時, 最後會有「之後再決定」.

      4. 檢查重述, 選擇下一步

        agent 用自己的話重述需求. 重述有固定的欄位:

        claude · 重述 (範例)
        Type: feature. list 增加新的輸出選項.Goal: list --count 在清單最後顯示列出的筆數.Problem: 現在 list 只列出待辦, 沒有總數.Decided: 總數跟著 --all / --done 篩選.Out of scope: 其他指令的輸出.Assumptions: (猜測) 沒有待辦時, 維持顯示 (沒有待辦).

        接著 agent 問一個問題. 這個答案同時代表「確認重述」和「選擇下一步」:

        確認AskUserQuestion
        上面的重述正確嗎? 接下來要怎麼做?
        1. 正確, 直接實作, 不寫文件(Recommended)小需求. 在這個 session 完成, 不產生 .mreq/ 文件.
        2. 正確, 先 grill, 不寫文件先用四象限檢查重述, 然後再重述一次.
        3. 正確, 寫文件再實作產生文件, 然後交給 mreq-apply.
        4. 有地方不對選出不對的項目, agent 會再問, 然後重新重述.

        選 第 1 個.

        觀察重點

        小需求才會出現「不寫文件」的選項組. 條件是需求為 Simple, 而且 Open (延後的決策) 是空的. 如果你在訪談時選了「之後再決定」, 這組選項就不會出現.

      5. 觀察實作與回報

        agent 先用一則短訊息列出 tasks, 每個 task 附上檢查方法. 然後一次做一個 task. 每個 task 都要執行某個指令來證明: 只讀程式碼不算證明.

        完成後, agent 對照重述回報: Goal 和每個 Decided 項目是「完成, 部分完成, 做法不同, 或缺少」, 附上 path:line. 它也會列出執行過的測試和結果.

      6. 自己驗證結果
        mreq-demo (範例輸出)
        npm run todo -- list -- --count[ ]   2  回覆客戶信件[ ]   3  繳電話費[ ]   3  準備週會簡報共 3 筆git status --short M src/cli.ts M test/todo.test.ts
        npm run todo -- list --count[ ]   2  回覆客戶信件[ ]   3  繳電話費[ ]   3  準備週會簡報共 3 筆git status --short M src/cli.ts M test/todo.test.ts

        git status 裡沒有 .mreq/. 這證明小需求流程不產生文件. 實際修改的檔案和輸出格式, 取決於你在訪談時的選擇. 你也會看到安裝 skill 產生的未追蹤檔案, 例如 .claude/. 這些檔案不是 agent 修改的.

      DEMO 2 · FEATURE · 約 15 分鐘

      加上到期日: 完整流程

      /mreq-define 待辦加上到期日, 過期要標示

      這是主要的 Demo. 你會走完 define, grill, apply, close 四個步驟, 中間可以選擇 commit. 這個需求會改到型別, 儲存資料, CLI 參數和輸出格式, 而且有好幾個決策要做. 所以 mreq 會建議寫文件.

      步驟 A: define, 訪談與重述

      1. 輸入指令
        claude · mreq-demo
        /mreq-define 待辦加上到期日, 過期要標示
      2. 觀察 agent 怎麼讀程式碼

        需求被判斷為 Complex 時, agent 會把閱讀工作分成 2 到 4 個角度, 例如「需求改到的程式碼和呼叫者」與「測試和執行方式」. 在 Claude Code 中, 你可能會看到它同時啟動幾個唯讀的 explorer subagent. 判斷為 Simple 時, 它會自己讀.

        兩種情況都可以. 重點是: 它讀完之後才開始問問題.

      3. 回答訪談問題

        feature 的訪談順序是: 完成的狀態, 誰使用, 什麼不在範圍內, 錯誤情況, 什麼資料要保存. agent 會一次問最多 4 個互相獨立的問題. 你可能會看到:

        日期格式

        --due 2026-12-01? 還是也接受 明天 這類寫法?

        過期的顯示

        在行尾加上文字標示? 還是改變排序?

        無效的日期

        輸入 2026-13-40 時, 要報錯還是忽略?

        舊資料

        現有的待辦沒有 due 欄位. 視為「沒有到期日」嗎?

        每個問題的推薦答案都在第一個. 想延後的決策, 選「之後再決定」. 延後的決策會寫進文件的 ## Open, agent 不會再問.

      4. 確認重述, 選「寫文件, 然後 grill」

        這次的確認選項是「寫文件」的選項組:

        確認AskUserQuestion
        上面的重述正確嗎? 接下來要怎麼做?
        1. 正確, 寫文件, 然後 grill(Recommended)計畫還沒經過檢查. 先壓力測試, 再實作.
        2. 正確, 寫文件, 然後實作寫完文件直接交給 mreq-apply.
        3. 正確, 只寫文件寫完文件就停止. 適合交給下一個 session.
        4. 有地方不對選出不對的項目, 回到訪談.
        觀察重點

        計畫感覺還沒經過檢查時, mreq 會把「寫文件, 然後 grill」放在第一個並推薦它. 選項文字每次都由 agent 重新撰寫, 但意思不變.

        2. 正確, 寫回文件, 停在這裡寫回後停止.
          3. 
              
        3. 正確, 寫回文件, 繼續 grill下一輪只檢查有變更的項目和仍未決的項目.
          4. 
              
        4. 有地方不對不寫入任何內容. 選出不對的項目, 再 grill 一輪.
          5.

      • 決策被推翻時, 文件會保留紀錄: Changed by grill: <原本的內容>.

        先看進度

        claude · mreq-apply

        2. 
        
      2. 
          
        看著 checkbox 一個一個打勾
        
          
        每個 task 的循環固定是: 重讀 Goal 和 Decisions, 做最小的修改, 執行指令證明, 打勾, 重寫 Handoff, 執行 update. 兩次打勾之間, 一定有一次 Handoff 重寫.

      3. 
          
        (選做) 實驗: 中斷後接續
        
          
        這個實驗展示文件為什麼是交接單.
        
          
          
            
        1. apply 做到一半時, 按 Esc 中斷 agent.
          2.

          3. 
            
        3. 觀察文件: 下一個未完成的 task 下方出現 - Resume: <已完成>; <剩下的>; <下一步>. 你說的話也會寫進這一行.
          4. 
            
        4. 輸入 /clear, 開始新的對話.
          5. 
            
        5. 輸入 /mreq-apply. 只有一份進行中的文件時, 它直接接續, 不用給路徑.
          6. 
            
        6. 觀察: 新的 session 從 Resume 那一行接續, 而不是從頭開始.

        4. 
        
      4.

      mreq-demo

      步驟 F: close, 核對後刪除
      
      
        
        
      1. 
          
        輸入指令
        
          
        
            
        claude · mreq-demo
        
            
        /mreq-closeClosing: D:/workspace/.../mreq-demo/.mreq/20261125-153012-todo-due-date.md
        
          
        
          
        只有一份 done 的文件時, 不用給路徑. 第一則訊息一定以 Closing: 開頭, 讓你確認它要關閉哪一份.
        
          
        你可以在同一個 session 執行, 也可以開新的 session. close 只依照現在讀到的文件和程式碼判斷, 不依照對話記憶.
        
        
        2. 
        
      2. 
          
        觀察稽核
        
          
        close 讀文件和文件引用的每個檔案. 然後對 Goal, 每個 ### Dn: 和每個打勾的 task 判斷: 完成, 部分完成, 做法不同, 或缺少, 並附上 path:line.
        
          
        文件是 done, 而且 Handoff 寫了驗證方法時, close 不會重跑測試. 它會在報告裡說明這件事, 但不會把它稱為「通過」.
        
          
        
            觀察重點
            
        close 的檢查不能改到真實資料. 需要執行會寫入檔案的檢查時, 它會改用新的路徑. 這個專案的 TODO_FILE 環境變數剛好可以做到. 觀察 agent 有沒有使用它.
        
          
        
        
        3. 
        
      3. 
          
        處理 finding (如果有)
        
          
        程式碼和文件不一致時, close 每個 finding 問一次: 引用文件的那一行, 說明程式碼的實際行為, 然後給你兩個選項:
        
          
        
            
        FindingAskUserQuestion
        
            
        D2 寫「過期在行尾標示 (過期)」. 程式碼在已完成的待辦也顯示了 (過期). 要怎麼處理?
        
            
          
              
        1. 接受程式碼把差異當成接受的偏離, 寫進報告.
          2. 
              
        2. 修正程式碼把 finding 交給 mreq-apply 修正. 文件不會被刪除.
          3. 
            
        
          
        
        
        4. 
        
      4. 
          
        刪除與報告
        
          
        所有問題都回答後, close 用 script 的 delete 刪除文件. 刪除之前, 它會先收集 ## Open 的項目, 因為檔案刪除後就沒有地方保存它們. 報告會列出: 刪除了什麼, 稽核結果, 接受的偏離, 以及後續事項.
        
          
        
            
        mreq-demo
        
            
        git status --short D .mreq/20261125-153012-todo-due-date.md
        
          
        
          
        如果你在步驟 E commit 過, git 歷史仍然保有這份文件. 沒有 commit 的話, 文件就永久消失.

      DEMO 3 · ISSUE · 約 8 分鐘
      
          
      修 bug: 重複的 id
      
          /mreq-define done 3 會同時勾掉兩筆
        
      
      
      
      
      這個 Demo 觀察 mreq 處理 bug 的方式. issue 類型有更嚴格的規則: 先重現, 再確認根因, 修的是原因而不是症狀.
      
      
        
        
      1. 
          
        先自己重現 bug
        
          
        為了不改到 todo.json, 這裡用 TODO_FILE 指向一個暫存檔. 以下是實際執行的輸出:
        
          
        
            
        mreq-demo

        只想用範例資料重現的話, 執行 npm run todo -- done 3, 再執行 npm run todo -- list -- --allnpm run todo -- list --all: 兩筆 #3 都會被勾掉. 結束後執行 npm run seed 還原.
        
        
        2. 
        
      2. 
          
        輸入指令
        
          
        
            
        claude · mreq-demo
        
            
        /mreq-define done 3 會同時勾掉兩筆
        
          
        
        
        3. 
        
      3. 
          
        觀察分類與訪談
        
          
        「應該 X 但是 Y」的描述代表行為錯誤, 所以 agent 會判斷為 issue. issue 的訪談順序是: 確切的重現步驟, 預期與實際, 從什麼時候開始, 影響到誰.
        
          
        重現步驟只有你知道時, agent 會請你輸入. 但它通常也會把自己的猜測當成選項提供. 把上一步的指令貼進文字欄即可.
        
          
        
            
        舊資料AskUserQuestion
        
            
        todo.json 裡已經有重複的 id. 修正 bug 之後, 這些舊資料要怎麼處理?
        
            
          
              
        1. 讀取時不處理(Recommended)只修新增的邏輯. 舊的重複資料列為 Follow-up.
          2. 
              
        2. 提供修復指令增加一個指令, 重新編號重複的待辦.
          3. 
              
        3. 之後再決定寫進 Open, 不影響修正 bug.
          4. 
            
        
          
        
          
        
            觀察重點
            
        這是這個 Demo 最有價值的問題: 修了 bug, 已經重複的資料也不會自己變好. 觀察 agent 有沒有主動問. 推薦的選項取決於 agent 的判斷, 可能和上面不同.
        
          
        
        
        4. 
        
      4. 
          
        觀察 issue 文件
        
          
        issue 模板有固定的 tasks. agent 會保留它們:
        
          
        
            
        .mreq/…-duplicate-id.md (節錄)
        
            
        ## Symptom- Repro: add A, add B, rm 1, add C, done 2- Expected: 只有 C 被標記完成- Actual: B 和 C 都被標記完成 ## Root CauseNot verified yet: id 用 todos.length + 1 產生 ## Tasks- [ ] 1. Reproduce the bug with the Repro above- [ ] 2. Confirm the root cause- [ ] 3. Fix, and show the Repro now passes- [ ] 4. Run the related tests
        
          
        
          
        注意 ## Root Cause: 驗證之前, 它一定寫成 Not verified yet: <假設>.
        
        
        5. 
        
      5. 
          
        確認重述, 選「寫文件, 然後實作」
        
          
        想再練習一次 grill 也可以選 grill. 這裡直接進入 apply, 觀察 issue 的規則.
        
        
        6. 
        
      6. 
          
        觀察 apply 的 issue 規則
        
          
          
            
        • 先重現: 修改程式碼之前, agent 會執行 Repro, 確認 bug 存在.
          • 
            
        • 確認根因: 只有在 ## Root Cause 寫入已驗證的原因和驗證方法後, 才開始修. 根因是 src/todo.ts:16 的 todos.length + 1.
          • 
            
        • 修原因, 不修症狀: 正確的修法是改變 id 的產生方式 (例如用現有最大的 id 加 1). 讓 done 只勾第一筆, 是修症狀.
          • 
            
        • 證明測試抓得到 bug: agent 可能會暫時還原修正, 確認新測試會失敗, 再恢復修正.
          • 
            
        • 兩次修正失敗就停止: 這代表根因可能是錯的. agent 會說明, 然後重新驗證根因.

      04 · 實際應用
      
      
      依情境選流程
      
      
      不是每件事都要走完整流程. 下表幫你選擇:
      
      
      
        
      情境流程
      
        
          
      需求明確, 改動小/mreq-define → 直接實作
      
          
      跨多個檔案, 或要分多個 sessiondefine → grill → apply → (commit) → close
      
          
      只有模糊的想法, 缺少術語/mreq-terms → /mreq-pro → /mreq-define (不給需求)
      
          
      看不懂現有的程式碼/mreq-how (加 --plain 給 PM)
      
          
      要把流程或架構畫成圖/mreq-graph
      
              
      
      
      
      延伸練習
      
      
        
        
      • 執行 /mreq-how done 指令怎麼找到要完成的待辦?, 打開 .mreq/how/ 下產生的 HTML.
        • 
        
      • 執行 /mreq-grill <path> 錯誤處理: 四象限仍然全部掃描, 但錯誤處理會問得更深, 而且先回報.
        • 
        
      • 執行 /mreq-terms 我想讓待辦可以重複, 然後輸入 /mreq-define 不給需求, 觀察它怎麼使用術語.

      05 · 疑難排解
      
      
      疑難排解與重置
      
      
      agent 說啟動目錄不是 git root, 然後停止
      
      
      離開 Claude Code, 用 cd 進入 mreq-demo, 再執行 claude.
      
      
      指令被拒絕 (denied)
      
      
      mreq 不會換一種方式重試. 它會列出被拒絕的指令和對應的 allow rule, 例如 Bash(uv run *mreq.py*), 然後停止. 用 /permissions 加入這條規則, 再重新執行.
      
      
      沒有安裝 uv
      
      
      skill 會自動改用 python, 找不到時再用 python3. 同一個對話只會切換一次.
      
      
      找不到 /mreq-define
      
      
        
        
      1. 確認你在 mreq-demo 目錄執行了 npx skills add, 而且有加 -a claude-code.
        2. 
        
      2. 確認 .claude/skills/mreq-define/SKILL.md 存在.
        3. 
        
      3. 離開 Claude Code, 再重新執行 claude.
        4. 
      
      
      
      agent 自己讀了 SKILL.md 並開始執行
      
      
      define 和 close 設定了 disable-model-invocation. 在 Claude Code 中, agent 不會自動執行它們. 其他 agent 可能不讀這個設定.
      
      
      重置 demo
      
      
      每個 Demo 之間可以重置到初始狀態. 下面的指令來自 README, 但 git clean 多了幾個 -e. 原因: -x 會刪除所有未追蹤的檔案, 包括安裝的 skill. 這幾個 -e 保留 skill.
      
      
      
        
      mreq-demo
      
        
      git reset --hard startgit clean -fdx -e node_modules -e .claude -e .agents -e skills-lock.jsonnpm run seed
      
      
      
      
      
        注意
        
      這些指令會刪除所有未 commit 的修改和未追蹤的檔案 (安裝的 skill 除外), 包括 .mreq/ 下的文件. start 是起點的 git tag. 要保留成果, 先在其他 branch commit.
      
      
      
    
      

    
      
      
      TAKEAWAY
      
      
      讓 agent 先問, 再做.

      • 文件與 Handoff: 讓下一個 session, 下一個 agent, 甚至下一個人都能接續工作.
        • 
        
      • close 的稽核: 只依照文件和程式碼判斷, 不依照對話記憶.
